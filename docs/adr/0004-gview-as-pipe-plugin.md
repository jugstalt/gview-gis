# gView as a plugin of gView.Pipe

gView.Pipe (the workflow app, sibling repository gview-pipe) gets nodes that read and write geodata through the gView dataset model: Read Features and Write Features, later spatial operations and network traces. The plugin `gView.Pipe.Plugins.Gis` lives here, because it needs most of gView and has to match the installed gView version. Pipe loads it from a gView folder (`Pipe:ExternalPlugins`, gview-pipe ADR 0044) into its own load context; its dependencies, the data sources included, come from that folder.

## Decisions

- **PlugInManager:** `PlugInManager.PluginDirectory` sets the folder scanned for `gView.*.dll`; without it, the folder of the entry assembly as before. Inside an isolated load context the plugins are loaded into that context (`AssemblyLoadContext.LoadFromAssemblyPath`), so their types share gView.Framework with the caller; in the default context it stays `Assembly.LoadFrom`. `gView.Pipe.*.dll` are never scanned: they reference the Pipe contracts, which only the Pipe host has.
- **Startup:** the plugin's `IPipePluginStartup` sets `PluginDirectory` to its own folder. Nothing else in gView knows about Pipe.
- **Contracts:** `gView.Pipe.Abstraction` is referenced as package with `ExcludeAssets="runtime"`; the host provides it. Until it is on nuget.org it comes from the sibling checkout (`nuget.config` next to the project, `dotnet pack src/gView.Pipe.Abstraction -c Release -o artifacts/packages` in gview-pipe).
- **Deployment:** the deploy build publishes the plugin (framework-dependent, per platform) and adds its files to the server and web apps ZIPs and Docker contexts without replacing any file of the app: only `gView.Pipe.Plugins.Gis.dll`, its `deps.json` and what the app doesn't have. So every gView installation contains the plugin; Pipe lists `<gView folder>/gView.Pipe.Plugins.Gis.dll` in `Pipe:ExternalPlugins`.
- **Development:** the build output of the plugin is a complete folder (it references the data sources it supports), so `Pipe:ExternalPlugins` can point at `src/gView.Pipe.Plugins.Gis/bin/Debug/net10.0/gView.Pipe.Plugins.Gis.dll`.
- **Feature classes:** the node Feature Class creates and deletes them through `IFeatureDatabase` of the dataset's database (OGC spatial databases such as PostGIS, the FDBs, shape files, GeoPackage, SpatiaLite); other data sources give an error. Truncate is `IFeatureUpdater.Delete(featureClass, "1=1")`.
- **Spatial nodes:** Geometry, Spatial Aggregate and Spatial Join read and write the GeoJSON items with SpatialNET.IO and compute with SpatialNET.Extensions, in the version gView uses (it lives in the same folder). No gView geometry is involved, so there is no conversion in between. They pass SpatialNET's reference factory (`ImpGeometryFactory`) explicitly and never set `SpatialNET.GeometryFactory.Default`, which belongs to the host. They compute in the coordinates of the items: operations with distances or areas refuse geographic coordinate systems (`srs` 4326, …), and inputs with different `srs` are an error, never projected silently.
- **Choice list of feature classes:** Read Features, Write Features and Copy Feature Class offer their feature class as a choice of the data source (`IPipeParameterOptions`, `PipeOptions`). The editor asks without a node context, so the nodes take `IServiceProvider` in a second constructor (the host creates them with `ActivatorUtilities`) and read the credential from `IPipeCredentialStore` and `IPipeSecretResolver`, both public Pipe contracts, so nothing changed in gview-pipe. Secrets of external sources are resolved as the node context does. Any problem (no credential, unreachable source) gives an empty list. A parameter with a choice list takes no expressions, so the feature class of these nodes is a fixed value; Feature Class keeps its text field, because Create needs a name that isn't there yet.
- **Read Features:** `Output` is Features, Distinct values (one item per combination of *Fields*, without id and geometry, computed while reading) or Count (one item `{ featureClass, count }`, the features read without attributes). *Order by* takes fields of the feature class with `asc`/`desc` and is never passed on as typed. *Offset* maps to `BeginRecord` of the filter; not every data source honors order and offset (shape files don't). *Filter geometry* also takes a bounding box `[minx, miny, maxx, maxy]`.
- **Write Features:** no transaction across batches (gView's updater has none, and the sources differ). *On error* is Stop (the default) or Skip item: with Skip item the node has an Error output (`IPipeDynamicPorts`, the port name `error` of the engine) with the items that failed and `error.message`; a failing batch is written again item by item to find the culprit. *Field mapping* (`field → property`) renames properties, *Unknown properties* ignore or fail (ignored names are logged once per run), *Write fields* is a positive list of fields after the mapping, *Write geometry* If present, Never or Always. Update leaves fields and geometry it doesn't get as they are.
- **Z values:** not supported. The GeoJSON conversion of the item is 2D on both sides, and SpatialNET works in 2D here; a node that needs Z would change `GisGeoJson`, the spatial nodes and their tests together.
- **Feature Class and Copy Feature Class:** *Additional fields* (an array of fields in the format of the schema: `name`, `type`, `size`, `precision`, `nullable`) and *Exclude fields* change the schema of Create; a name that is there already is an error. There are no default values, rename or change of the geometry type. Copy Feature Class streams from a cursor into batches of the target, never holding all features, and builds the target with the code of Create (so it needs *Allow schema changes* for Create and Replace, not for Append). The source projects into the srs of the target. Source and target must not be the same feature class of the same credential. The output is one item `{ source, target, copied, seconds }`.
- **Spatial nodes, later operations:** Geometry has Offset curve (left positive), Smooth (Chaikin, iterations) and Point at distance (a distance or a fraction of the length, optional offset to the side). Spatial Aggregate has Polygonize (lines are unioned first so crossings are nodes; lines that enclose nothing give no polygon) and a clip polygon or bounding box for Voronoi (same srs as the items). Spatial Join has Cut (polygons or lines of main along the lines of overlay, one item per piece with the properties of its main feature) and Locate along line (the nearest overlay line of each main point: `position`, `fraction`, `offset` and `distance` as properties with the prefix, the line's properties as in a join; the point can snap to the line). Locating needs a projected srs. Not done: Linear referencing with M values, Z.
- **Tests:** `gView.Pipe.Plugins.Gis.Tests` run the nodes with a small fake node context against a gView FDB in a SQLite file. Shape files can't be used for writing: gView can't update or delete in them.

## Consequences

- Building `gView-gis.sln` needs the package from gview-pipe in its `artifacts/packages` until the package is published.
- Code that finds its files relative to the entry assembly (`Assembly.GetEntryAssembly()`), e.g. SpatiaLite's native libraries via `AppContext.BaseDirectory`, WMS templates or UI dialogs, looks in the Pipe folder when gView runs inside Pipe. That doesn't matter for reading and writing features; fix such places when a node needs them.
